# 踩过的坑：被实测推翻的「合理推断」

> 记录一次完整调研里，看起来很有道理、但被实测推翻的推断。
> 本文件的价值不在具体结论（那些在别的条目里），而在**提醒推断的失败率有多高**。

## 五条被推翻的推断

| 当时的推断 | 实测结果 | 错在哪 |
| --- | --- | --- |
| 隐藏建筑会打断合批 | `Transparency=1` 渲染代价为 **0** | 拿 Cities: Skylines 的「合并 mesh」机制外推；Roblox 是 instancing |
| Decal 不合批，招牌必须烘进 UV | 同贴图的 100 个 decal 只 **+1 批** | 官方文档 "decals don't batch well" 说的是**不同贴图**的情况 |
| 手工 LOD 得不偿失 | 切换代价为零，且能在中距离用上低模，**该做** | 上面两条错误叠加出来的结论 |
| `RenderFidelity.Automatic` 在 Studio 里不降级 | 会降，只是阈值在 600~900 stud 之间 | 测量范围不够远，只测到 600 就下结论 |
| LOD 阈值按屏幕占比 | 按**绝对距离**（×1/×3/×10 首降点全一样） | 拿「文档数字对不上」硬凑了一个解释 |

## 共同的失败模式

1. **跨引擎类比。** 三条错误里有两条源于「CS 是这样，Roblox 应该也是」。
   Cities: Skylines 的 `RenderGroup` 合并 mesh 是有反编译实证的，
   但那个实证只对 CS 成立。**别的引擎的实证不是本引擎的证据。**

2. **相信官方文档。** 官方文档的 LOD 阈值（250/500 stud）与实测不符；
   "decals don't batch well" 的表述省略了关键前提。
   **文档也要当作待验证的假设。**

3. **测量范围不够就下结论。** `Automatic` 那条只差再测一个距离点就能发现。
   下结论前先问：**我的测量覆盖了参数空间的哪一段？边界外我知道吗？**

4. **用一个未验证的解释去圆另一个未验证的观察。**
   「文档说 250 但实测 900」→「所以一定是按屏幕占比」——
   这是在猜测上叠猜测。正确做法是设计一个能判别的实验（缩放法），几分钟就有答案。

## 正确的做法

Roblox 闭源、不让写 shader，看起来只能猜。但实际上：

- `Stats.FrameRateManager.Batches` 可从 Lua 读
- `run-in-roblox` 能把 Lua 塞进 Studio 全自动跑
- 20 行脚本 + 3 分钟 = 一个确定答案

**只要有可能测，就不要猜。** 具体方法见 `measurement.md`。
